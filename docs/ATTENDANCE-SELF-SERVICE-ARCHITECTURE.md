# Attendance Self-Service Architecture

Employees previously had no way to see their own current attendance status, and no visibility into two real automatic mechanisms that affect them (a biometric scan silently ending an open remote session, and a scheduled end-of-day auto-clock-out). This doc covers the frontend widgets, the notification rules, and the data-correctness fixes built to close that gap. For the existing HR/Team/My Attendance CRUD pages themselves (list/overview pages, RPCs), see `DEPARTMENT-PAGES-TABLES.md` and `RPC-REFERENCE.md`; for the notification system's own generic architecture (event log, rules, fan-out), see `NOTIFICATIONS-ARCHITECTURE.md`.

## The policy this is all built around

**Office and Blending Plant are scanner-only. The app's clock-in form is remote-only** (Site Visit, Work From Home, Business Meeting, Training, Overtime). These are mutually exclusive by design — you're either physically badged in at a company site, or clocked in remote via the app, never represented as both at once for the same moment. This matters for every design decision below.

## "Current activity" — why `employees_public.current_status`, not `unified_daily_attendance.daily_activities`

`unified_daily_attendance.daily_activities` (a `STRING_AGG` of that day's `attendance_activities` rows) is populated **exclusively** from app clock-ins. Given the policy above, it can never represent a scanner-based "Office"/"Blending Plant" day — an on-site-only day always has an empty `daily_activities`, which is why an early version of the Dashboard card showed nothing for on-site employees.

`employees_public.current_status` (`supabase/sql_editor/employees_public_view.sql`) already solves this: a real-time `CASE` that returns whichever of {an open app session, the most recent biometric scan, an approved leave entry} happened most recently today —

- an **open** app session more recent than the last scan → the attendance type's name (e.g. "Site Visit")
- a **closed** app session that's the most recent event → `'Offline'`
- the most recent event is a scan → `scanner_location` verbatim (e.g. `"Office"`, `"Blending Plant"`)
- nothing today at all, but an approved leave entry exists → `'On Leave (<code>)'`
- otherwise → `'Offline / Not Arrived'`

Every string this produces already matches an exact key in `src/components/attendance/attendanceType/AttendanceType.jsx`'s config map, so it renders with the correct icon/color with zero new styling work. `unified_daily_attendance.hr_flag` is kept as a *secondary* anomaly badge alongside it (Pending App Approval / Missing App Check-Out / Incomplete Card Scans / Absent / OK / Approved / Weekend), since `current_status` carries no approval-state information.

## Frontend

- **`src/features/employee/attendance/private/hooks/useMyCurrentStatus.js`** — wraps the pre-existing `fetchEmployeePublicById` (`src/features/hr/employees/public/api/employeePublic.js`) in a `useQuery` (`refetchOnWindowFocus: true`, overriding the app-wide default — this view is a live snapshot). Shared by both consumers below so nav and dashboard never disagree.
- **`src/features/employee/attendance/private/hooks/useMyAttendanceThisWeek.js`** — a narrow query against `unified_daily_attendance` for the current employee, Monday-through-today. Supplies both today's row (`hr_flag`, `first_in`/`last_out`, `daily_activities`, `is_on_leave`) and the week's `hours_worked` series for the chart.
- **`src/components/attendance/todayAttendanceCard/TodayAttendanceCard.jsx`** — the Dashboard home page card. Shows the `current_status` pill, the `hr_flag` anomaly badge, a first-in/last-seen completion bar, a horizontal-bar chart of hours worked this week, and the clock-in/out action. When there's an open remote session, a live "Xh Ym" elapsed-time counter (`src/functions/useElapsedSince.js`) is shown instead of relying on `last_status_time` — that field freezes at the clock-in moment for as long as a session stays open (it only moves again on the next real event), so it would otherwise look stale for the whole session.
- **`src/components/attendanceActivityClockin/clockinMini/ClockinMini.jsx`** — the sidenav/mobile-nav mini widget. Shows the same `current_status` pill (via the same shared hook) when there's no open app session; an open session still takes precedence, since it's the most authoritative "right now" signal.
- **`src/features/employee/attendance/private/hooks/useClockInOutAction.js`** — the shared clock-in/out wiring (sidebar state, mutation calls, query invalidation for both `my_attendance_this_week` and `my_current_status`) used by both components above, so a clock-in/out from either surface updates both immediately.

## Notification rules

All three follow the existing generic event-driven system unchanged (`notification_events` → `notification_rules` → `notifications`/`email_queue`, see `NOTIFICATIONS-ARCHITECTURE.md`). Recipients for all three are the employee themselves, resolved via `target_payload_keys: ['employee_profile_id']`.

| Event type | Shape | Files |
| --- | --- | --- |
| `attendance.clocked_in_remote` | Change-triggered, `AFTER INSERT ON attendance_activities` | `supabase/functions/notify_attendance_clocked_in.sql`, `supabase/triggers/trg_notify_attendance_clocked_in.sql` |
| `attendance.autoclockout_approaching` | Scheduled-scan, two cutoffs, one-shot per cutoff | `supabase/functions/check_attendance_autoclockout_approaching_evening.sql`, `..._midnight.sql`, `supabase/sql_editor/attendance_activities_add_autoclockout_warning_columns.sql`, `supabase/sql_editor/schedule_check_attendance_autoclockout_approaching_cron.sql` |
| `attendance.clocked_out_remote` | Change-triggered, `AFTER UPDATE ON attendance_activities WHEN (OLD.clocked_out_at IS NULL AND NEW.clocked_out_at IS NOT NULL)` | `supabase/functions/notify_attendance_clocked_out.sql`, `supabase/triggers/trg_notify_attendance_clocked_out.sql` |

Seed rules: `supabase/sql_editor/seed_attendance_autoclockout_notification_rules.sql` (the first two events), `supabase/sql_editor/seed_attendance_clocked_out_notification_rule.sql` (the third, seeded separately since the first file had already been executed by the time the third event was added — re-running it would have duplicated its two rows).

### The two real auto-clock-out cutoffs

`auto_clock_out()` (`supabase/functions/auto_clock_out.sql`) force-closes any still-open remote `attendance_activities` row. It's scheduled **twice daily** against two live `pg_cron` jobs — around **5:00 PM MYT** and **11:59 PM MYT** — both calling this same function. As with the older of the two (per `NOTIFICATIONS-ARCHITECTURE.md`'s own note on `auto-clock-out.ts`), **neither cron schedule is captured anywhere in this repo** — both were set up directly in the Supabase dashboard. `attendance.autoclockout_approaching`'s two scan functions are timed ~15 minutes ahead of each (16:45 / 23:44 MYT) to warn anyone still open before it happens.

### `attendance.clocked_out_remote` covers all three closure paths with one trigger

Every code path that ends a remote session — the employee's own manual clock-out (`clockOutAttendanceActivity`), a scanner badge auto-closing it (`auto_clock_out_app_on_scan()`), and the two cutoffs above (`auto_clock_out()`) — already converges on the same `UPDATE attendance_activities SET clocked_out_at = ...`. Rather than three separate `emit_notification_event()` call-sites, one trigger on that transition covers all three, with a best-effort reason inferred from data already on hand (no new columns, no cross-function signaling):

- an exact `clocked_out_at` = `attendance_logs.scanned_at` match for that employee → scanner-caused, names the location
- `clocked_out_at`'s local time-of-day falls in a narrow window around 17:00 or 23:59 MYT → cutoff-caused
- otherwise → manual

## Scanner race-condition guard (`auto_clock_out_app_on_scan()`)

`vigilance_iot` ingests scans in ~5-minute batches (per `CRON_SCHEDULE`, both scanner locations), so a scan's real timestamp can differ meaningfully from when its `attendance_logs` row actually lands. The pre-existing trigger (`supabase/triggers/trigger_auto_clock_out.sql`) had no guard against this at all — it closed *any* currently-open session the moment *any* new scan landed, with no check on timing. Two guards were added to its `UPDATE`'s `WHERE` clause:

- **Ordering** (`clocked_in_at <= NEW.scanned_at`): a scan whose real timestamp precedes the session's own clock-in can no longer close it — prevents a delayed/out-of-order scan from producing a negative-duration row.
- **Minimum gap** (`NEW.scanned_at >= clocked_in_at + interval '5 minutes'`): matches the ~5-minute ingestion cadence — a scan landing within 5 minutes of the clock-in is too close/ambiguous to confidently mean "arrived on-site instead," so it's ignored and the session stays open. The next real scan or the end-of-day cutoff still closes it eventually.

## `hours_worked` — multi-segment scanner day fix

`unified_daily_attendance`'s hardware-hours figure (`hw_hours`) was a naive `MAX(scanned_at) - MIN(scanned_at)` span across every scan that day — correct for a simple one-visit day, but silently counting any away-gap (a remote stint, even a long lunch) as on-site time. Since `app_hours` separately, correctly counts that same remote gap, the total (`hw_hours + app_hours`) double-counted it on any office→remote→office (or office→remote→blending-plant, etc.) day.

**Rejected fix: pairing scans by position (1st↔2nd as in/out, and so on).** This looked like the obvious fix, but employees routinely forget to scan in or out in practice — a single missed scan shifts the odd/even parity for every scan later that day, silently mispairing the rest and producing worse, harder-to-notice errors than the original bug. This would only be safe with strict, hardware-enforced alternation (impossible to scan "in" twice without an "out" between), which isn't realistic given how attendance actually gets used.

**Actual fix**: keep the naive day-span, but subtract whatever portion of it overlaps with a real, independently-tracked remote session (`attendance_activities` — unambiguous start/end times, nothing to "forget" the direction of). This only needs each day's *outer* scan bounds, so it's immune to any number of missed or extra scans in between, and is location-agnostic (the hardware span already merges every scanner location, so an office→blending-plant→office day is handled identically to a single-location day). New CTE `daily_hw_remote_overlap` in `supabase/sql_editor/hr_unified_daily_attendance_view.sql`; `hours_worked` becomes `GREATEST(0, hw_hours - overlap_hours) + app_hours`.

**What this still doesn't fix, deliberately**: a travel/absence gap with *no* corroborating `attendance_activities` row at all (a pure lunch break, or physically moving between two on-site locations with nothing logged in between) is still counted as on-site time, unchanged from before. This is a separate problem from the one reported, and isn't solvable by a calculation change — it needs a real per-scan in/out type at the hardware level, which the scanner doesn't currently provide.

## `last_out` fallback for an open session

`unified_daily_attendance`'s `app_check_out` (feeding `last_out`/`last_out_time`) only ever looked at `clocked_out_at` — for a still-open remote session that's always `NULL`, so an employee actively clocked in with no checkout yet contributed nothing to "last seen" from the app side at all. `employees_public.current_status`'s own `app.latest_event_time` already had the right fallback for this exact concept (`GREATEST(clocked_in_at, COALESCE(clocked_out_at, epoch))`, effectively "use `clocked_in_at` if there's no checkout yet"). `daily_app`'s `app_check_out` now does the same: `MAX(CASE WHEN approval_status != 'Rejected' THEN COALESCE(clocked_out_at, clocked_in_at) ... END)`. `app_hours` is deliberately left untouched — an open session still contributes 0 hours, not `now() - clocked_in_at`, since a live-updating, non-idempotent value would be wrong for a settled data view. `get_attendance_dashboard_rpc.sql` reads `last_out` directly from this view rather than recomputing it, so this was the one place that needed the fix.

## Scan-log verification — RLS, an RPC, and the timeline card

HR or an employee had no way to verify the individual scan timestamps behind a summarized "Office"/"Blending Plant" timeline card (`attendance_activity_audit`'s `hw_events` rows are a per-location-per-day summary — first scan, last scan, count — not the raw punches). Fixed with three pieces:

- **`supabase/policies/attendance_logs_crud.sql`** — `attendance_logs` had RLS enabled with zero policies since it was created (per `docs/TABLE-POLICIES.csv`), so a direct client `SELECT` always silently returned nothing; the existing timeline only ever worked through `attendance_activity_audit`/`unified_daily_attendance`, two plain views that bypass RLS via view-owner privileges. Added the same 4-tier shape already established for this exact kind of data in `supabase/policies/leave_ledger_crud.sql` (self / superadmin / HR department / direct manager), bridged through `employees.employee_id` (the text scanner code `attendance_logs.employee_id` stores, not the `employees.id` uuid `current_employee_id()` returns). SELECT-only — the only writer is `vigilance_iot`'s service-role key, which bypasses RLS entirely and is unaffected.
- **`supabase/functions/get_attendance_log_scans.sql`** — a plain (not `SECURITY DEFINER`) RPC, so it runs under the caller's own privileges and the RLS policies above apply exactly as they would to a direct query. Exists only because PostgREST's query builder can't express the `DATE(scanned_at AT TIME ZONE 'Asia/Kuala_Lumpur') = p_work_date` bucketing every other attendance surface already uses.
- **`AttendanceTimelineCard.jsx`** — a Hardware row (`event_source === "Hardware"`) is now clickable ("Verify Scans"), lazy-fetching (`useAttendanceLogScans`, only once expanded) and inline-expanding to show the raw scan timestamps. Unconditional across every `mode` — purely read-only verification. Since this component is the one shared implementation behind HR Attendance Management, My Attendance, and Team Attendance's list-page sidebars, this one change covered all three. `TodayAttendanceCard.jsx` got its own "Today's Activity" section separately, reusing the same `fetchEmployeeDayDetails` call `AttendanceSidebarHR.jsx` makes and rendering through the same `AttendanceTimelineCard`, passed a new `mode="readonly"` — a value that intentionally matches none of the component's existing `hr`/`self`/`manager` action-button gates, so no clock-out/approve/edit buttons render there (the card already has its own clock-in/out button elsewhere).

## The `NaN%` bug

`AttendanceSidebarHR.jsx`'s day-summary bar always showed `NaN%`. Root cause: it built its chart data with `.toFixed(2)` values (strings, not numbers), and `CustomLegend.jsx`'s percentage math (`data.reduce((sum, d) => sum + d.value, 0)`) did string concatenation instead of addition when fed strings — e.g. `0 + "6.50" + "1.50"` → `"06.501.50"`, a string with two decimal points that `Number()` can't parse, so the percentage was `NaN / total * 100` every time. Fixed at both ends: the immediate call site now passes real numbers, and `CustomLegend.jsx`'s reduce now coerces with `Number(d.value)` — that component is shared by other chart cards, not attendance-specific, so the hardening protects any other caller making the same mistake.

## The day-timeline bar

Replaced the binary "Worked vs Remaining" bar in `AttendanceSidebarHR.jsx` with a real per-activity-type, time-ordered bar (`src/components/attendance/attendanceDayTimelineBar/AttendanceDayTimelineBar.jsx`), reusing `timelineData` already fetched for the Activity Timeline below it — no new query. Two design points worth recording, both reconsidered mid-build:

- **Custom flex-div bar, not `StackedBarRenderer`.** Reusing the existing Recharts-based `StackedBarRenderer` was evaluated (its actual constraint — collapsing `data[]` into one object keyed by `name` — is solvable with unique per-segment names) but explicitly rejected in favor of keeping this component's own concern to one thing: proportional time segments via plain flex-basis widths, not a stacked bar chart built for a different shape of problem.
- **A guaranteed-minimum 8am–6pm window that widens, never clips.** The first version hard-clipped anything outside 8–6 — actively misleading, not just less detailed: someone who worked 7am–8pm would render an identical-looking "full" bar to someone who worked exactly 8–6, silently hiding the extra hours on both ends. Fixed: `windowStart = min(8:00 AM, earliest real segment start)`, `windowEnd = max(6:00 PM, latest real segment end)` — the 8–6 range is always at least fully present (for cross-employee/cross-day comparability, since HR reviews many of these in sequence), but the window grows outward for any real early/late activity instead of hiding it. Axis labels reflect the actual computed bounds, not a hardcoded "8:00 AM"/"6:00 PM".
- Leave rows (`event_source === "Leave"`) have neither `check_in_time` nor `check_out_time` — not clock-time-anchored at all — so they're excluded from this bar entirely; the existing "On Leave" chip above it already covers that case.
- **`src/components/tooltip/Tooltip.jsx`** — a new generic hover-tooltip component, built because none existed (only Recharts-specific `CustomTooltip.jsx`, and `SideNavLink.jsx`'s own one-off inline implementation, never extracted for reuse). Attaches its ref/hover handlers directly onto its child via `cloneElement` (not a wrapper `div` with `display: contents`, which would make `getBoundingClientRect()` unreliable), and portal-renders to `document.body` so it's never clipped by a scrolling/overflow-hidden ancestor like the sidebar panel. Each bar segment uses it instead of a native `title` attribute.

**One new shared component**, since none existed — every prior multi-badge card hand-rolled its own conditional `StatusBox` block: `src/components/attendance/attendanceAnomalyBadges/AttendanceAnomalyBadges.jsx`, taking `{ overtimeHours, isEarlyLeave, isLateArrival }` and rendering 0–3 `StatusBox`es (confirmed the right/only primitive for this — `StatusBadge` is for enum-like statuses, `AttendanceType` is for activity/location). Wired into every day-summary surface:

Its `hr_flag`→`StatusBox` color logic was also switched from a hand-duplicated ternary to the shared `getHrFlagStatusType()` helper (`src/functions/attendanceFlagStatus.js`), so this card can't silently disagree with every other `hr_flag` consumer.
- **`AttendanceSidebarHR.jsx`** — its original hand-rolled OT/Early-Leave block replaced with the shared component (same visual result, Late Arrival now included too).
- **`TodayAttendanceCard.jsx`** — `overtime_hours` was already fetched and unused; `is_early_leave`/`is_late_arrival` needed adding to `fetchMyAttendanceThisWeek`'s explicit column list (`myAttendanceService.js`) first.

**Deliberately left alone**, confirmed with the user: `AttendanceTimelineCard.jsx` (the per-activity card inside the sidebar) has no natural per-activity OT/early/late concept — these are inherently day-level facts (first arrival vs. last departure *of the day*), not per-punch ones. The Employees directory (`EmployeeCard.jsx`/`EmployeesPublicList.jsx`/`EmployeeProfile.jsx`) reads `employees_public`, a structurally different real-time "who's around right now" snapshot with no equivalent columns — extending it there would need genuinely new SQL on that view, not just new JSX, and was scoped out rather than forced in.

## Leave/attendance conflict detection

HR2000's leave ledger (`leave_ledger_entries`) records only a day fraction (0.5 or 1) per entry, with no morning/evening distinction, and nothing previously cross-checked a recorded leave entry against what actually happened in `attendance_logs`/`attendance_activities` that same day. Three new boolean columns on `unified_daily_attendance`, appended last per this view's append-only constraint, all reusing `daily_leave.leave_day_fraction_total` (which already `SUM`s multiple entries per employee/day, to support a legitimate AM+PM split across two different leave types):

- **`is_leave_attendance_conflict`** — a FULL day's leave is on record (`leave_day_fraction_total >= 1`) yet real attendance also exists that day (`hw_check_in`/`app_check_in` not null). Either the leave should have been revoked, or it was entered against the wrong date in HR2000.
- **`is_insufficient_half_day_hours`** — a HALF day's leave is on record (`leave_day_fraction_total = 0.5`) but `hours_worked` (the same expression the view's main `hours_worked` column uses — repeated here rather than referenced, since a SELECT list can't reference a sibling column's own alias, the same constraint `overtime_hours`/`is_late_arrival` already document) comes in under 4 hours. Deliberately does **not** require a check-in to exist separately — a half-day leave with zero attendance logged at all for the working half already satisfies `0 < 4`, catching that case with the same flag rather than needing a fourth one.
- **`has_leave_fraction_error`** — this employee/day's leave entries sum to *more* than one full day (`leave_day_fraction_total > 1`) — a duplicate entry, or a half-day and full-day both logged against the same date. Physically impossible, always an HR2000 data-entry mistake, independent of attendance.

All three are populated regardless of which `hr_flag` branch fired, same precedent `is_on_leave`/`leave_type_codes`/`leave_day_fraction` already established — the conflict is itself the finding, so it shouldn't be masked by whichever work-based branch happened to win.

**`attendance_activity_audit`** can't compute these itself — they're day-level aggregates, and a single event row has no visibility into the day's total hours or summed leave fraction. Rather than duplicate that logic a second time (the exact kind of drift the `hours_worked` and `09:00` threshold fixes above were about eliminating), the view's `UNION ALL` was wrapped in a CTE (`all_events`) and `LEFT JOIN`ed to `unified_daily_attendance` by `(employee_uuid, work_date)`, reusing its single source of truth. Every row for a given employee/day carries the same three flags, but the frontend (`AttendanceTimelineCard.jsx`) only surfaces them on the `Leave` row — that's the row a reviewer would actually open to act on. Since this view is only ever queried scoped to one employee + one day (`fetchEmployeeDayDetails`'s `.eq(...).eq(...)`), the added join stays cheap regardless of `unified_daily_attendance`'s own size.

**Frontend**: `AttendanceAnomalyBadges.jsx` gained three more optional props (`isLeaveAttendanceConflict`, `isInsufficientHalfDayHours`, `hasLeaveFractionError`), wired into the same three day-summary surfaces as the OT/Early/Late badges (`AttendanceCard.jsx`, `AttendanceSidebarHR.jsx`, `TodayAttendanceCard.jsx` — the last needing its `fetchMyAttendanceThisWeek` column list extended again, same as last time). While wiring `AttendanceCard.jsx`, found and fixed a pre-existing bug: the whole `<AttendanceAnomalyBadges>` block was wrapped in `{activity.overtime_hours > 0 && (...)}`, silently hiding every other badge (early leave, late arrival, and now these three) on any day with no overtime — redundant besides, since the component already self-guards via its own internal `hasAny` check.

Also added to the HR Attendance Management List's filters (`filterConfig.js` + `attendanceOverviewService.js`'s `applyAttendanceFilter`), matching the existing `lateArrival`/`earlyLeave` toggle shape — `leaveAttendanceConflict`, `insufficientHalfDayHours`, `leaveFractionError`. Unlike `overtimeOnly`/`lateArrival`/`earlyLeave`, these need no `hr_flag` exclusion (Weekend/Absent) — they're already tightly scoped by `leave_day_fraction_total` itself.

**Deliberately left alone**, same boundary as the OT/Early/Late badge pass: nav/current-status widgets (`ClockinMini`, `useMyCurrentStatus.js`) and the Employees directory (`employees_public` — different grain). No new KPI card was added to `get_attendance_dashboard_rpc.sql` for these flags — not requested this pass.

## Incomplete Card Scans excluded from hours aggregates

`daily_hardware`'s `hw_hours = MAX(scanned_at) - MIN(scanned_at)` computes exactly `0.00` on a single-scan ("Incomplete Card Scans") day — not a deliberate rule, just `MIN == MAX` with nothing to diff against. That 0 then flowed into `hours_worked` (and, via it, `overtime_hours`) as if it were a *known* zero-hour day, and nothing downstream excluded it from `avg_hours_worked`/`overtime_hours_total`/`hoursWorkedTrendData`/`topOvertimeData` in `get_attendance_dashboard_rpc.sql` — `Weekend`/`Absent`/`On Leave` rows were already excluded from these same aggregates (the exact `is_on_leave` dilution-bug fix documented in that RPC's own comments), `Incomplete Card Scans` was simply missed. The fix is a pure aggregation-filter addition (`and hr_flag <> 'Incomplete Card Scans'` alongside the existing exclusions) — no view change needed, since `hr_flag`/`hours_worked` were already computed correctly; the bug was only in which rows the RPC's averages/sums included. Mirrored into `get_hr_reports_dashboard_rpc.sql`'s own `overtime_hours_total`, which that file's own header comment already documents as deliberately kept in sync by copy with the Attendance RPC.

Deliberately **not** touched: `avg_check_in_time`/`avg_check_out_time`, `is_late_arrival`/`is_early_leave`, and the presence/roster denominators (`workingDayRecordsCount`/`attendanceRatePct`/`absenteeismRatePct`/`present_*_count`) — an Incomplete Card Scans day still correctly counts as *present* (they did show up), only its *hours* are unknown, not its presence.

## Paid vs. unpaid leave

`leave_ledger_types.is_paid` (e.g. `NPL` = No-Pay Leave) existed in the schema but was never read anywhere in the attendance view/RPCs/frontend — `leaveDaysCount` treated every leave day as equivalent regardless of pay impact, which is a real gap for a page whose own header comment already describes itself as usable "for payroll prep."

**`hr_unified_daily_attendance_view.sql`**'s `daily_leave` CTE now also computes `paid_leave_day_fraction`/`unpaid_leave_day_fraction` (`SUM(day_fraction) FILTER (WHERE lt.is_paid)` / `FILTER (WHERE NOT lt.is_paid)`), appended as two new nullable columns at the end of the view (its append-only constraint), matching `leave_day_fraction`'s own existing uncoalesced convention. `get_attendance_dashboard_rpc.sql`'s `employee_leave_rows`/`prev_employee_leave_rows` (the latter now also joining `leave_ledger_types`, which it previously didn't need to) feed three new KPIs: `paidLeaveDaysCount`, `unpaidLeaveDaysCount`, `prevUnpaidLeaveDaysCount`. Mirrored into `get_hr_reports_dashboard_rpc.sql`'s `period_leave`/`kpi_leave_totals` for the same "kept in sync by copy" reason as the hours fix above (frontend for that page untouched — only its RPC number stays correct). The Attendance Overview's "Leave Days" tile (`overviewConfig.js`) gained two sub-metrics: `Unpaid Leave Days` (raw count) and `Unpaid vs Prev. Period` (delta, same `calcDelta`/`deltaText`/`deltaIcon` pattern as the tile's existing total-leave delta).

**Important caveat, carried only in code comments (not the UI), by explicit user decision**: `is_paid` is itself an unconfirmed guess for nearly every leave type today — `leave_ledger_types.needs_hr_confirmation` is `true` for all but one seeded row (`RPL`), and hyrax-data-platform's own migration comment says these values are "best guesses pending real HR sign-off... must be confirmed with HR/payroll before ever driving a payroll calculation." The paid/unpaid split above surfaces `is_paid` at face value, with no warning banner — matching this codebase's existing convention of disclosing this kind of assumption only in code comments (`is_late_arrival`'s 09:00 threshold, `payrollCyclePresets.js`'s `PAYROLL_CYCLE_START_DAY`), not in the UI. Anyone wiring this into an actual payroll calculation must confirm `is_paid` per leave type with HR/payroll first.

## Public holidays & company off-days

HR provided three CSVs (`supabase/csv/kl-ph.csv`, `meru-ph.csv`, `kl-meru-off-day.csv`) from HR2000. Previously, `hr_flag` only special-cased Saturday/Sunday — a real company holiday with no scans was indistinguishable from an unexcused `Absent`. A dead `leave_holidays` table existed (`country_id`/`state` shape, zero rows ever written, zero RLS policies) — dropped rather than revived; wrong shape for this need.

**New table `public_holidays`** (`supabase/sql_editor/public_holidays_migration.sql`): `work_location_id` (nullable — `NULL` means "applies to every location"), `holiday_date`, `code` (HR2000's own code, traceability only), `name`, `category` (`national`/`state`/`company`). A unique index on `(work_location_id, holiday_date)` uses `NULLS NOT DISTINCT` (Postgres 15+) so re-running the seed can't duplicate a company-wide row — the default `NULLS DISTINCT` behavior would otherwise never consider two `NULL`-scoped rows a conflict.

**Dedup rule, found by actually diffing the two location CSVs, not by trusting the code prefix**: most `N` (national) rows are identical in both files, and most `S` (state) rows appear in only one — but `S09` (Nuzul Al-Quran) appears identically in *both* `kl-ph.csv` and `meru-ph.csv`, since that state holiday happens to be observed in both Selangor and the Federal Territory. The one-time seed collapses any (code, date, description) that matches across both files into a single `NULL`-scoped row; everything else keeps its specific location. This is a one-time load, not a recurring sync (unlike `leave_ledger_entries`'s weekly HR2000 import) — HR maintains the table from here through the new admin page below.

**RLS**: read is `for select to authenticated using (true)` (`project_categories_crud.sql`'s shape — company-wide reference data, no per-employee ownership); write is HR-department-or-superadmin (`addresses_crud.sql`'s exact two-policy shape) — deliberately not the 4-tier self/manager pattern personal data like `leave_ledger_crud.sql` uses.

**`hr_unified_daily_attendance_view.sql`**: a new `daily_holiday` CTE resolves at most one holiday per employee-day (`DISTINCT ON`, preferring a location-specific row over a `NULL`-scoped one on the rare date both exist), feeding two new always-populated columns — `is_public_holiday`, `public_holiday_name` — same "populated regardless of which `hr_flag` branch fired" precedent as `is_on_leave`. `hr_flag`'s `CASE` gets a new `'Public Holiday (<name>)'` branch, checked *before* the weekend check (more specific/informative, and most Malaysian holidays fall on weekdays anyway). Someone who actually worked on a holiday still correctly falls through to `Approved`/`OK` — but `is_public_holiday` stays true regardless, preserving the fact for a future OT-rate signal (`docs/PAYROLL-DATA-REQUIREMENTS.md`). `active_company_dates` (the view's date spine) also now unions in every `public_holidays.holiday_date` — without this, a date with truly zero scans anywhere in the company (the common case on a major holiday) would never generate a row for anyone at all, silently hiding the very flag this feature exists to show. This is a pre-existing gap Weekend/Rest Day still has (not fixed here, out of scope) — holidays needed it fixed since it would otherwise defeat the point.

**`hr_attendance_activity_audit_view.sql`**: a new `holiday_events` CTE mirrors `leave_events` exactly (one synthetic row per employee per applicable holiday, no check-in/out times), so a holiday's Activity Timeline shows a real card instead of "No app activities logged for this day." `AttendanceTimelineCard.jsx` gained an `event_source === "Holiday"` branch mirroring the existing `"Leave"` one. `AttendanceDayTimelineBar.jsx` needed no change — Holiday rows have no `check_in_time`, so they're excluded from the bar by the same filter that already excludes Leave rows.

**RPC denominators** (`get_attendance_dashboard_rpc.sql` + `get_hr_reports_dashboard_rpc.sql`, kept in sync by copy): `and not is_public_holiday` added alongside every existing `hr_flag <> 'Weekend / Rest Day'`/`not is_on_leave` exclusion on presence/roster/anomaly-rate denominators (`present_*_count`, `working_day_records_count`, `late_arrivals_count`, `early_leave_count`, `workChannelMixData`, `dailyAttendanceTrendData`, `departmentAttendanceData`) — a company holiday isn't a working day regardless of whether one person happened to come in, exactly like Weekend. Deliberately **not** added to `avg_hours_worked`/`overtime_hours_total` — unlike Incomplete Card Scans, a holiday's hours are genuinely knowable (0 if nobody worked, real hours if someone did), so excluding it would hide real holiday-worked time. `hrFlagBreakdownData` buckets `'Public Holiday (...)'` into one flat `'Public Holiday'` category before grouping, same treatment `'On Leave%'` already gets.

**Frontend**: since `hr_flag` now carries a dynamic name suffix here too, the List page's `publicHoliday` filter is a boolean toggle (`is_public_holiday`), mirroring `onLeave`'s own existing workaround rather than trying to fit it into the fixed `hrFlag` enum. `AttendanceType.jsx` gained a second `startsWith("public holiday")` branch alongside its existing `"on leave"` one, same reason.

**New admin page**: `AttendancePageLayout.jsx` already had a commented-out "Settings" tab scaffolded (`GearIcon`, `/app/hr/attendance/settings`) — uncommented and implemented rather than inventing new navigation, since holiday management belongs directly with the module it feeds. `AttendanceSettings.jsx` is modeled on `ITAssetManagement.jsx` — the one confirmed full add/edit/delete precedent in this codebase (`DataSidebar` doubling as Add/Edit, `ActionModal` confirming save/delete) — deliberately without pagination/search/sort, since a year's holiday calendar is a small, complete list (~30 rows) HR wants to see all at once. Its card view (`PublicHolidayCard.jsx`) is modeled on `LeaveCard.jsx` (the closest existing shape: a date badge + a categorical label pill, no per-employee assignment concept) rather than `ITAssetList.jsx`, since a holiday isn't assigned to one employee.

## Reconciling attendance on public holidays

`is_public_holiday` (above) deliberately left one thing for later: when an employee actually works *on* a holiday, the day still correctly falls through to `Approved`/`OK` in `hr_flag` — but nothing surfaced that fact anywhere HR would notice it before payroll. Two more columns close that gap, both appended last on `unified_daily_attendance`:

- **`is_worked_on_holiday`** — existence-based (`hw_check_in`/`app_check_in` present on a holiday date), mirroring `is_leave_attendance_conflict`'s own check rather than `hours_worked > 0`, so a data quirk that computes 0 hours despite a real check-in still counts as "attended."
- **`holiday_hours_worked`** — the concrete number HR reconciles against payroll. **Scope, confirmed with the user**: hours only, not an estimated payable/rate figure — applying Malaysia's Employment Act holiday-pay convention would need an unconfirmed policy multiplier (the same kind of guess already left unconfirmed for `leave_ledger_types.is_paid`), and would revisit the earlier decision that this app is a Payroll Input Package, not a payroll engine (`docs/PAYROLL-DATA-REQUIREMENTS.md`).

`hr_flag` itself is deliberately unchanged — a worked holiday stays `Approved`/`OK`, exactly how overtime doesn't override `hr_flag` either. The fact surfaces additively instead, at every layer already established for day-level payroll facts:

- **`hr_attendance_activity_audit_view.sql`** — the two columns ride along on the join to `unified_daily_attendance` this view already has (no new join needed); the Holiday timeline card shows "Worked Xh on this holiday" when true.
- **`AttendanceAnomalyBadges.jsx`** — a new blue (not red — this is a payroll fact, not an error) badge, wired into the same three day-summary surfaces as every other badge here.
- **`tableConfig.jsx`** (Attendance List's Table view) — a new "Holiday Worked" column, mirroring the existing "Leave" column's exact convention — the most literally visible reconciliation surface, a real grid column rather than a badge inside a card.
- **`filterConfig.js`/`attendanceOverviewService.js`** — a new `workedOnHoliday` boolean filter, the actual reconciliation pull-list HR uses before running payroll (distinct from `publicHoliday`, which includes holidays nobody worked at all).
- **Both dashboard RPCs** — a new "Holiday Work" KPI (`holidayHoursWorkedTotal`/`employeesWorkedOnHolidayCount`, `+prevHolidayHoursWorkedTotal` on the Attendance RPC only — HR Reports has no prev-period concept anywhere), mirroring the Overtime Hours tile's exact shape and placed next to it on the Attendance Overview page.

## Odd/even in-out pairs visualized inside every timeline card (HR auditing)

A Hardware card's `check_in_time`/`check_out_time` is a `MIN`/`MAX` summary across possibly several raw `attendance_logs` scans that day — a day with 4 Office scans (in, out for lunch, in, out) shows as one "8:36 AM → 5:32 PM" card, with no visibility into the fact that they actually left and came back. HR wants to see the real in/out pattern, purely to judge whether stricter scanner discipline (always scan in AND out, never skip) needs enforcing.

**First attempt (superseded): splitting `hw_events` into one row per pair.** Initially built by rewriting `attendance_activity_audit`'s `hw_events` CTE so each odd/even pair became its own card. **Reverted** — the user clarified they want to keep exactly one Office card and one Blending Plant card per day (matching every other surface's expectation of "one card per location"), with the pairing shown *inside* that one card instead of splitting it into several. `hw_events` is back to its original one-row-per-employee-per-location-per-day `MIN`/`MAX` shape.

**Actual design: the pairing lives entirely in `AttendanceTimelineCard.jsx`, client-side, reusing data already being fetched.** The existing scan-log-verification hook (`useAttendanceLogScans`, backed by `get_attendance_log_scans.sql`) already returns every raw scan for that card's (employee, location, day) in chronological order — previously fetched lazily, only once HR clicked "Verify Scans". Now fetched eagerly whenever `event_source === "Hardware"`, since the pair breakdown built from it is this card's primary content, not a supplementary drill-down. `scansExpanded` still gates only the fully-raw, ungrouped scan list further down (renamed "Show/Hide Raw Scan Log" to distinguish it from the pair breakdown above it).

Pairing itself: `scans[0]` = in, `scans[1]` = out, `scans[2]` = in, ... (`pairedSegments`, a plain `.reduce()` over the already-fetched array) — a trailing unpaired scan (odd count) gets `check_out_time: null`, rendered as "no matching out scan yet". **Purely a display aid**: this never touches `hours_worked`/`hr_flag`, which stay computed independently by `unified_daily_attendance`'s own `daily_hardware` CTE (positional odd/even pairing was deliberately rejected for *that* calculation earlier this session — employees routinely forget to scan in or out, which would corrupt a positional pairing there; that reasoning is unaffected by this purely-visual reuse of the same idea).

**"Use the same bar component as the main full attendance bar"**: `pairedSegments` is fed directly into `AttendanceDayTimelineBar` — the exact same component `AttendanceSidebarHR.jsx`'s day header and `TodayAttendanceCard.jsx` already use for the whole day — passed synthetic `{attendance_type, event_source, check_in_time, check_out_time}` objects instead of real `attendance_activity_audit` rows. Same visual language, same hover tooltips, same gap-filling for a genuine gap between two on-site sessions, zero changes to that shared component. Underneath the bar, an explicit text list spells out each pair's exact time range and duration (e.g. "1. 8:36 AM – 12:01 PM (3h 25m)") — `formatPairDuration()`, a small local helper — since HR auditing needs this always visible, not hidden behind a hover tooltip.

**Extended to App cards too, for visual consistency across every card, not just Hardware.** An `attendance_activities` row already *is* one clean clock-in/clock-out session — there's no raw-scan concept to pair — so `pairedSegments` for an App row is just a one-item array built directly from `activity.check_in_time`/`check_out_time`. Both event sources now share one code path for the bar + breakdown list; only the *source* of `pairedSegments` differs (fetched raw scans for Hardware, the activity's own fields for App).

**The old "TEST VISUAL BAR" (`StackedBarRenderer`, "Worked" vs "Remaining" out of a flat 8h) is removed** from `AttendanceTimelineCard.jsx` entirely, replaced by the pairing bar above. `StackedBarRenderer`/`VerticalStackedBarRenderer` remain in use elsewhere (`EmployeeOverview.jsx`, `ITAssetOverview.jsx`) — this removal is scoped to the attendance timeline card only, not the shared chart components themselves.

**Two separate hour totals, not one**, shown under the pair list: **First In → Last Seen** is the naive full span (`activity.check_in_time` to `activity.check_out_time`, what the old stacked bar's "Worked" value used to show) — an "Ongoing" label when there's no check-out yet. **Total From Pairs** sums only the *complete* pairs' durations (a trailing unpaired scan has no check-out to measure, so it's excluded, not counted as zero elapsed time). For a genuine multi-scan Hardware day, the two numbers diverge by exactly however much time fell *between* scanned pairs (e.g. an unscanned lunch break) — the headline audit signal this whole feature exists to surface. For App, and for a clean single-pair Hardware day, they're identical by construction.

## Weekend as an independent flag, not folded into `hr_flag`

HR found the List/Overview confusing while testing: "weekend" only existed as the string `hr_flag = 'Weekend / Rest Day'`, assigned only when nobody clocked in that day — the moment an employee actually worked a Saturday, the fact "this was a weekend" disappeared entirely (`hr_flag` just became `'Approved'`/`'OK'`, indistinguishable from any weekday). This silently caused a real bug: an employee voluntarily working a Saturday and arriving at 10am got flagged `is_late_arrival = true`, exactly as if it were a normal workday, since the flat 09:00/17:00 thresholds had no exception for a non-workday. Same bug affected public holidays.

Fixed with a new, independent, always-on `is_weekend` boolean (`expected_shifts`, `EXTRACT(ISODOW FROM work_date) IN (6,7)`), computed purely from the calendar regardless of whether any activity happened that day — unlike `hr_flag`, this never changes based on what the employee actually did. The `'Weekend / Rest Day'` branch was removed entirely from `hr_flag`'s CASE; a genuine unworked weekend now falls through to the same `'Absent'` fallback a real unexcused absence uses (a deliberate decision, confirmed with the user — status should only reflect real attendance outcomes now, not calendar facts). `is_late_arrival`/`is_early_leave` are now guarded `NOT is_weekend AND holiday_name IS NULL`, so neither ever fires on a weekend or public holiday regardless of whether real attendance exists that day.

**Frontend consequence, fixed in the same pass**: since a genuine unworked weekend now reads `hr_flag = 'Absent'`, every render site would show a red "Absent" badge on every Saturday/Sunday unless corrected. `src/functions/attendanceFlagStatus.js` gained `getDisplayAttendanceFlag(hrFlag, isWeekend)`, a display-only override used everywhere `hr_flag` renders as a `StatusBox` (`AttendanceCard.jsx`, `AttendanceSidebarHR.jsx`, `TodayAttendanceCard.jsx`, `tableConfig.jsx`'s Status column): shows "Weekend" (grey) instead of "Absent" (red) when `is_weekend && hr_flag === "Absent"`, otherwise passes the real `hr_flag` through unchanged — plus a small additional "Weekend" tag alongside the real status on a day someone actually worked a weekend, so the calendar fact is never lost either way. All filters/KPIs continue to query the raw `is_weekend`/`hr_flag` columns directly; the override is presentation-only.

**A correctness bug this surfaced, found by direct code read**: `get_attendance_dashboard_rpc.sql`'s `absent_days_count`/`prev_absent_days_count`/"Top Absenteeism" leaderboard did `hr_flag = 'Absent'` with **no weekend exclusion at all** — safe only because weekend and absent used to be different `hr_flag` values. Fixed to `hr_flag = 'Absent' and not is_weekend` in all three places; every other place in both dashboard RPCs that previously excluded `hr_flag <> 'Weekend / Rest Day'` was swapped to `not is_weekend`.

**Caveat logged for anyone reading `hr_flag` directly in future work**: `hr_flag = 'Absent'` alone no longer means "unexcused absence on a working day" — it also matches every unworked weekend (and would need `and not is_public_holiday` too, for an unworked holiday, though that case already has its own distinct `hr_flag` string). Any future query/report/payroll extract filtering on `hr_flag = 'Absent'` must add `and not is_weekend`, or it will count every unworked Saturday/Sunday as an unexcused absence — this had already gone stale in `docs/PAYROLL-DATA-REQUIREMENTS.md`'s own "Days absent" row before being caught and corrected.

Since Holiday Work and Overtime Hours were both already tracked as Overview KPIs, but Weekend Work wasn't despite `is_weekend` now existing, added `is_worked_on_weekend`/`weekend_hours_worked` to `unified_daily_attendance`, mirroring `is_worked_on_holiday`/`holiday_hours_worked`'s exact shape (existence-based — `hw_check_in`/`app_check_in` present, not `hours_worked > 0` — so a data quirk that computes 0 hours despite a real check-in still counts as "attended"). ## Overtime calculation bug: window had no floor on its start

`overtime_hours` computed `last_out_time − 18:00` with no lower bound on the window, silently assuming continuous presence from 6PM regardless of actual arrival time — an employee whose entire day started after 6PM (e.g. clocked in 9PM, out 11PM) showed 5h of overtime instead of the real 2h. Fixed by bounding the window's start to the later of (actual first arrival, 6PM): `last_out_time - GREATEST(first_in_time, TIME '18:00:00')`. Verified null-safe (`GREATEST` ignores `NULL` rather than propagating it, so a true absence still computes 0 exactly as before) and inert for a normal day (arrival before 6PM still picks 18:00 as the floor). View-only fix — every downstream consumer (`overtime_hours_total`/`employees_with_overtime_count`/`topOvertimeData` in both RPCs, the `overtimeOnly` filter, `AttendanceAnomalyBadges`, the Overview tile) reads this one column directly, so nothing else needed to change.

## "Present Only" filter's over-exclusion bug

`presentOnly` did `.eq("is_weekend", false).neq("hr_flag", "Absent")` — the separate `is_weekend = false` check was not just redundant (an unworked weekend already reads `hr_flag = 'Absent'`, so excluding `'Absent'` alone already excludes it) but actively wrong: it also excluded a **worked** Saturday, even though the employee was clearly present that day. Fixed to `.neq("hr_flag", "Absent").not("hr_flag", "ilike", "Public Holiday%")` — the second clause added at the same time, same reasoning, to also exclude an unworked Public Holiday (previously not excluded at all, since its `hr_flag` reads `'Public Holiday (name)'`, never `'Absent'`). Safe because `hr_flag` only ever reads that string prefix on a day with zero real activity — a worked holiday falls through to `Approved`/`OK`/etc., so this can never wrongly exclude a day someone actually worked, mirroring exactly how excluding `'Absent'` already can't.

## Performance regression from the weekend spine, and a CTE-materialization trap

Adding weekend calendar dates to `active_company_dates` (above — so a weekend with zero company-wide activity isn't silently missing from the spine, mirroring the pre-existing public-holiday fix) caused a real production regression: `get_attendance_dashboard`/`get_hr_reports_dashboard` calls scoped to a full year and every department started returning `57014 canceling statement due to statement timeout`, and even narrower (3-4 month) ranges got measurably slower (from ~2s to ~4-5s). Root-caused to three compounding issues, in the order found and fixed:

1. **`get_company_activity_dates()` was missing a `STABLE` marker**, defaulting to `VOLATILE`. Fixed — it's a pure read with no side effects, correctly `STABLE`. A non-`ANALYZE` `EXPLAIN` looked deceptively fine at this point in the investigation — its own row estimates were badly wrong (`rows=6` surviving a full-year, company-wide filter, which should have been a red flag on its own) — the lesson logged here: a plain `EXPLAIN` never executes the query and can't be trusted when a function-based row source is involved; `EXPLAIN (ANALYZE, BUFFERS)` is the only reliable diagnostic in that situation.
2. **`get_attendance_dashboard_rpc.sql`'s `period_rows`/`prev_period_rows` (and `get_hr_reports_dashboard_rpc.sql`'s `period_attendance`) are each read by 15-25 separate scalar-subquery KPIs**, with no `MATERIALIZED` hint — added explicitly, so the (expensive) base view only gets computed once per period per call regardless of planner heuristics.
3. **The actual root cause**, found via `EXPLAIN (ANALYZE, BUFFERS)`: `expected_shifts` (the employees × date-spine cross join) was referenced **twice** inside `unified_daily_attendance` — once by `daily_holiday`, once by the final outer `SELECT`. Postgres's default behavior for a non-recursive CTE referenced more than once is to materialize it in full, *before* any outer date-range filter (from the RPC's `period_rows`) can reach it — so every query against this view, regardless of the caller's requested range, paid the full cost of cross-joining every active employee against the *entire* multi-year date spine (real activity dates + every public holiday + every generated weekend date) before any filtering happened. This explains both symptoms: narrower ranges got slower because the spine itself got bigger (the new weekend dates), and the full year still timed out because retaining and joining a whole year out of that unfiltered matrix finally tipped it over. Fixed by rewriting `daily_holiday` to join `public.employees` directly (it only ever needed `employee_uuid`/`work_location_id`, never the full date-spun cross product) — removing the second reference lets `expected_shifts` become eligible for inlining. `EXPLAIN (ANALYZE, BUFFERS)` confirmed real predicate pushdown afterward (`Rows Removed by Filter` now shows up right at the `get_company_activity_dates`/`generate_series`/`public_holidays` scans, not only after the full cross join) and a real ~416ms execution time for a 5-month range.
4. **Complementary, lower-risk safety margin**: the weekend `generate_series` bound was tightened from 3 years back to 2 (still comfortably covers a full-year report plus its year-over-year delta comparison) — reduces the unavoidable fixed cost of the `get_company_activity_dates()`/`generate_series` branches, which can't have filters pushed *inside* them (an opaque function call; a plain `generate_series` call's bounds aren't reliably pushed down either), regardless of how well the rest of the query optimizes.

**Logged for future attention, not yet acted on**: `get_company_activity_dates()`'s row estimate is still generic — Postgres defaults an opaque function's cardinality guess to a placeholder, and no explicit `ROWS n` was set. Confirmed via `EXPLAIN (ANALYZE)`: `rows=5` estimated vs. `rows=141` actual for one branch on a 5-month window (roughly 1000x off at the top-level plan node, `rows=11` vs `rows=10944`). Not currently a problem — the chosen plan (indexed nested loops against `departments`/`employees`/`profiles`/`work_locations` via their primary keys) tolerates the misestimate fine at current data volume — but as headcount/history grows, or if a future query shape joins this same date source against a larger, less-indexed table, the same class of bug (a query that looks cheap to the planner but is actually reading everything) could resurface. Fix, when convenient: `SELECT COUNT(*) FROM get_company_activity_dates();` to get the real distinct-date count, then `ALTER FUNCTION public.get_company_activity_dates() ROWS <that number>;` — a pure metadata hint, no behavior change.

## The App activity "Edit" form was missing its own data (`attendance_activity_audit` didn't carry it)

HR's inline "Edit" form for an App timeline card (`AttendanceTimelineCard.jsx`'s `DataForm`, columns from `tableConfig.jsx`'s `attendanceActivityTableConfig`) silently failed to preselect the current Attendance Type, and never showed the existing Notes value either — both fields rendered as if blank, even when the underlying `attendance_activities` row genuinely had them set. Scoped fix: only this "Edit" form (`isEditing === "edit"`) was touched — the separate Clock In/Clock Out quick-edit sub-forms (`changeClockInTimeConfig.jsx`/`changeClockOutTimeConfig.jsx`) are unrelated and untouched, per the user's explicit ask.

**Root cause**: `rowData={activity}` for this form comes from `attendance_activity_audit` (`fetchEmployeeDayDetails`), not the raw `attendance_activities` table — and that view's `app_events` CTE never selected `attendance_type_id`, `photo_url`, or `notes` at all. `attendance_type` on this view is only the *joined display name* (`at.name`, a plain string like `"Site Visit"`) — not the real foreign-key id the edit form's `<select>` needs to match against `attendanceTypes` options to preselect the right one. `DataForm.jsx` seeds its initial form state via `col.getValue(rowData) ?? ""` — with the real fields simply absent from `rowData`, every one of these columns silently seeded as `""`, no error, just a blank-looking field.

**Fix**: `app_events` now also selects `aa.attendance_type_id`, `aa.photo_url`, `aa.notes` directly (all three already sitting right there on the joined `attendance_activities aa` row — no new join needed). `hw_events`/`leave_events`/`holiday_events` get matching `NULL` placeholders of the same types, appended at the same position, to keep the `UNION ALL` column list aligned — App is the only event source this edit form ever applies to, so `NULL` is correct and expected for the other three. `tableConfig.jsx`'s `getValue` expressions for these columns were already correct (`activity.attendance_type_id`, `activity.notes`) — they just had nothing real to read before. Also fixed in passing: `displayValue: (activity) => activity.attendance_type?.name` (dead code — `DataForm.jsx` never reads `col.displayValue` at all, confirmed by grep — but wrong regardless, since `attendance_type` is already a plain string here, not a nested `{name}` object) → `activity.attendance_type`.

**Note on `CREATE OR REPLACE VIEW`'s positional constraint, since this fix hit it directly**: the first attempt added the 3 new columns to `app_events`' own `SELECT` list (right after `remarks`) and left the final outer `SELECT` as `ae.*, uda.col1, ...`. That broke the Studio push with `cannot change name of view column "is_leave_attendance_conflict" to "attendance_type_id"` — because `ae.*` expands *before* the explicit `uda.*` columns in that outer `SELECT`, so the 3 new columns landed ahead of the 5 pre-existing `uda.*` ones instead of after them, shifting every one of their positions. Fixed by replacing `ae.*` with an explicit column list (the original 13 `ae` columns, in their original order, then the 5 `uda` columns, then the 3 new `ae` columns last) — a real trap worth remembering: `ae.*` is not automatically "safe" for append-only edits just because the new columns were themselves appended inside `app_events` — what matters is their position in the view's *final* output, which depends on where `ae.*` itself sits relative to any columns added after it in the outer `SELECT`.

## Clock In/Clock Out: a time-only editor + reusable cross-field date ordering

The "Edit Clock In"/"Edit Clock Out" sub-forms used to use `editor: "dateTime"` (a native `datetime-local` input) — letting HR accidentally change the activity's *date*, when only the *time* should ever be corrected. Two genuinely reusable pieces came out of fixing this (not attendance-specific, despite living in this doc because that's where the need originated):

- **`editor: "time"`** (`src/components/dataTable/editors/TimeEditor.jsx`, registered in `Editors.jsx`) — a native `<input type="time">`. Takes one new optional prop, `referenceDate` — the date to re-attach to the entered time-of-day, computed by `DataForm.jsx` from a column's new `getReferenceDate(rowData)` hook and passed through to every editor (harmless/unused by every other editor type). Falls back to the field's own current value's date when `referenceDate` isn't given. `changeClockInTimeConfig.jsx`/`changeClockOutTimeConfig.jsx` both set `getReferenceDate: (activity) => activity.work_date`, so editing either time always keeps the activity's real calendar date — including when setting a still-`null` `clocked_out_at` for the first time. Two new helpers back this: `toMYTTimeInputValue()`/`combineMYTDateAndTime()` (`src/functions/formatDate.js`) — both explicitly Asia/Kuala_Lumpur-aware (fixed `+08:00` offset; Malaysia has no DST) rather than relying on the *viewer's own browser timezone* the way the pre-existing `DateTimeEditor.jsx` does — a real correctness gap for a value being **written**, not just displayed, matching the same seriousness `AttendanceDayTimelineBar.jsx`'s `minutesInMYT()` already treats this with elsewhere.
- **`col.validate(value, { rowData, formValues })`** (`DataForm.jsx`) — a new generic column-config hook for cross-field ordering constraints, wired into `Controller`'s `rules.validate`. Receives *both* `rowData` (for two fields that don't even share a form — Clock In and Clock Out are two separate single-field forms, so "the other" timestamp is a value on the row, not a sibling form field) and live `formValues` from `watch()` (for fields that genuinely do share one form). Returning a string sets that as the field's RHF error message; `onError`'s toast was fixed to prefer that real message over its previous hardcoded "X is required" (which used to fire regardless of *why* validation failed).
  - Attendance: Clock In must be strictly before Clock Out and vice versa (checked against `rowData.check_out_time`/`check_in_time` — the *other* mini-form's field, unavailable any other way).
  - Employee Management (`employeeManagement/list/tableConfig.jsx`, unrelated to attendance but sharing this same new mechanism): `join_date` must be strictly earlier than `confirmation_date`, `end_date` (Contract End Date), and `resignation_date` (Termination Date) each, checked against `formValues.join_date` (a true sibling field in the same employee edit form). Confirmed with the user: no ordering is enforced *between* those three — Contract End Date and Termination Date represent different, likely mutually-exclusive exit reasons, not a sequence.

**Known limitation, not solved**: an activity that genuinely spans midnight (clocked in late one night, clocked out just after midnight the next day) can't be perfectly represented by a single `work_date` anchor — editing "Clock Out Time" forces the *same* calendar day as `work_date`, not the true next day. Pre-existing in how the app models a day's activity; not something this pass introduces or attempts to solve.
