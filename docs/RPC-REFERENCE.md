# Dashboard RPC Reference

Field-by-field, formula-level reference for every dashboard-backing Postgres RPC in `supabase/sql_editor/`. This documents the **deployed `.sql` files in this repo** — the as-built calculations — not the target data model. For that target (SAP schema, star-schema plan, department KPI frameworks), see `hyrax-data-platform/docs/sap-data-architecture-plans/`; that repo is still just a plan, not what's implemented. For the narrative/module view of each dashboard (what page renders it, known gaps), see [`DASHBOARD-CURRENT-STATE.md`](./DASHBOARD-CURRENT-STATE.md) — this file complements that one with exact formulas, it doesn't replace it.

**Deploy mechanism, same for all four:** hand-pasted into Supabase Studio's SQL editor. No CLI/migrations/CI wired up for RPCs — editing the `.sql` file in this repo does **not** change production until someone manually re-runs it in Studio. If a dashboard's numbers don't match what's in this doc, check the live function definition first (`select pg_get_functiondef('<function_name>'::regproc);`) before assuming the calculation is wrong.

**`get_finance_dashboard` carries function-scoped `set statement_timeout = '30s'`/`set work_mem = '64MB'` in its own signature** (added 2026-07, after a filterless dashboard load started hitting Postgres error `57014` — the PostgREST API role's `statement_timeout` is materially tighter than a Studio session's, and the GL rollout's added row volume tripped it). These are part of the `CREATE FUNCTION` statement itself, not a separate `ALTER FUNCTION` run once by hand, specifically so they survive every redeploy — don't strip them as dead-looking config when copy-editing this function.

**Conventions used throughout, defined once here:**

- SAP date columns are stored as `text` — every comparison casts `"column"::date`.
- SAP boolean-ish flags are the strings `'Y'`/`'N'`, not real booleans — `is_cancelled = 'N'` means active/non-voided. Revenue must never blend cancelled docs into an active total.
- **GP sanitization guard**: `sap_*.gross_profit` has a known item-cost master-data defect at the extremes (legitimate gp/total_amount_myr ratios top out ~2.7x; defective rows run 900x-1000x+). Anywhere GP is summed, rows where `abs(gross_profit) > abs(total_amount_myr) * 5` are nulled out before summing — the row's revenue/count is untouched, only its GP contribution drops.
- **The RCT2 join trap**: `sap_payment_applications.payment_ref` joins to `sap_payments.doc_entry` — never `receipt_number` (diverged from `doc_entry` for receipts after 2024-12-20; see `hyrax-data-platform/docs/data-dictionary.md`). Separately, `sap_payment_applications.doc_entry` is the real FK to `sap_invoices.doc_entry`, but **only** when `inv_type = 13` — it's a polymorphic FK (14/18/19/24/203/other point at document types not extracted here). A payment application with `inv_type != 13` legitimately can't be attributed to an invoice or its rep — that's expected, not a bug.
- **GL sign convention** (added 2026-07): `sap_gl_accounts.current_balance`/`current_balance_myr` is uniformly debit-positive — Assets store positive as-is, but Liabilities/Equity/Revenue (credit-normal) store **negative** and must be negated to report a human-readable positive amount. `sap_gl_journal_lines.debit_amount`/`credit_amount` are unaffected (already split into non-negative columns). Confirmed live via a balance-sheet identity check (Assets + Liabilities + Equity ≈ 0). See `hyrax-data-platform/docs/data-dictionary.md`'s "GL Hierarchy & Sign Convention" for the full derivation and the confirmed chart-of-accounts category codes (100/200 under Assets, 300 under Liabilities, etc.) this RPC's `gl_account_ancestry_raw` recursive CTE resolves.
- **`employee_sales_rep_mapping`** is the only valid bridge from SAP's `sales_rep_code` to Supabase `employees.id` (for display — avatar/name — never for attribution math). `sap_sales_persons.employee_id` (EmpID) is confirmed broken: empty in production, and conceptually wrong (references SAP's unused HR module). See `DASHBOARD-ROADMAP.md` §1.1.
- **Point-in-time vs. period-bound**: fields scoped by `p_start_date`/`p_end_date` are period flows; fields explicitly marked "as of today" ignore the date filter entirely (aging, backlog, stock position) because they're snapshot balances, not period activity.

## `get_finance_dashboard`

Backs Finance Reports (`FinancialReports.jsx`). Through 2026-06 this was mostly an AR/cash subledger, plus a Gross Profit read straight off SAP's own per-invoice `GrosProfit` field (added 2026-07). **Finance Expansion Phase 1 (2026-07)** added the mirror-image Accounts Payable chain (bills received, cash paid, AP aging, DPO, top vendors). **Finance Expansion Phase 2 (2026-07)** added a real General Ledger extraction and, with it, this RPC's first true P&L (`netProfit`, `netProfitMarginPct`, an approximate `ebitda`) and balance-sheet ratios (`currentRatio`, `quickRatio`, `workingCapital`) computed from actual GL postings. **Finance Expansion Phase 3 (2026-08)** added a genuine, GL-derived (indirect method) Statement of Cash Flows — `cashFlowStatementData`/`cashFlowWaterfallData` below — after a live investigation found SAP B1's own native Cash Flow Categories module (`OCFW`/`OCFT`) had never actually been used (6 empty placeholder rows, last touched 2021); built instead from data already live from Phases 1-2, strengthened by a genuine bonus finding from that same spike, `sap_bank_account_movements` (OBNK), a real per-bank-account monthly movement record used for a second reconciliation check. **Phase 5 (2026-08)** added `balanceSheetStatementData` — the full Level-3 line-item Statement of Financial Position, reusing the same account-ancestry work Phase 3's investigation had already done, rather than the 4-bucket `currentAssets`/`fixedAssets`/`currentLiabilities`/`totalEquity` summary that's all `kpis` ever exposed. **Phase 6 (2026-08)** added `incomeStatementData` — the proper statement-order presentation of the same GL P&L figures `plBreakdownData` already exposed as a chart shape, plus a `viewAllTo` link on Finance Reports' "P&L Breakdown" card through to it. Statement of Changes in Equity is confirmed feasible from data already live but not yet built (see `06-finance-expansion-execution-plan.md`'s Phase 6 notes). See `hyrax-data-platform/docs/sap-data-architecture-plans/06-finance-expansion-execution-plan.md` for the full build and `hyrax-data-platform/docs/data-dictionary.md`'s "GL Hierarchy & Sign Convention" before trusting or extending any GL-derived field below.

**Performance rewrite + YoY/trend additions (2026-07, post-Phase-2):** a filterless page load was taking 20-25s even after the `statement_timeout`/`work_mem` fix above — traced to `kpi_totals` computing ~35 fields as independent correlated subqueries (e.g. 8 separate scans of `base_gl_lines` alone). Rewritten into 8 single-pass aggregate CTEs (`invoices_agg`, `payment_apps_agg`, `payments_agg`, `bills_agg`, `vendor_payment_apps_agg`, `vendor_payments_agg`, `gl_agg`, `gl_balance_agg`), each computing every field it owns with `sum(...) filter (where ...)` instead of N subqueries — the same pattern `get_sales_leads_dashboard`/`get_sales_reports_dashboard` already use below. `kpi_totals` itself still exists, now just a cross join of these single-row aggregates, so every field name/formula is unchanged. Same pass also added three YoY fields (`yoyPeriodInvoicedRevenue`, `yoyPeriodGrossProfit`, `yoyNetProfit` — same period one year back, distinct from the existing `prevPeriod*`/`prevNetProfit` fields which compare to the immediately preceding period) and two new chart datasets (`plTrendData`, `opexBreakdownData`).

**Signature:**

```
get_finance_dashboard(
  p_customer_code  text    default null,
  p_sales_rep_code bigint  default null,
  p_start_date     date    default null,
  p_end_date       date    default null,
  p_is_cancelled   boolean default null,  -- null/false = active docs ('N'); true = cancelled-only audit view ('Y')
  p_status_code    text    default null,  -- shared across AR (sap_invoices) and AP (sap_vendor_bills) — both use the same 'O'/'C' DocStatus convention
  p_vendor_code    text    default null   -- added 2026-07 (Finance Expansion Phase 1), AP mirror of p_customer_code
)
```

No new parameter was needed for Phase 2 — P&L is scoped by the existing `p_start_date`/`p_end_date`, and the balance sheet is company-wide and point-in-time (no customer/vendor/rep dimension applies to a GL account).

**`kpis` is built from 4 `json_build_object` calls merged via `jsonb ||`, not one (fixed 2026-07):** the `kpis` object grew to 50+ key/value pairs (100+ arguments) across every phase's additions, which hit a hard Postgres limit — `json_build_object`/`jsonb_build_object` cap at 100 arguments (`FUNC_MAX_ARGS`, not a config setting), and exceeding it raises error `54023`, "cannot pass more than 100 arguments to a function." Split along the same domain boundaries the field table below is already organized by (AR core / AP chain / GL P&L / Balance sheet), each comfortably under the limit with room to grow. **If you're adding a new `kpis` field**, add it to whichever of the 4 blocks it belongs with — if a block ever approaches ~45 pairs again, split it further rather than letting it hit the ceiling.

**Base CTEs:**

- `base_invoices` — `sap_invoices` filtered by `is_cancelled`, `customer_code`, `sales_rep_code`, `status_code`. Carries `gross_profit_sanitized` (the GP guard above).
- `base_payments` — `sap_payments` (ORCT header), filtered by `is_cancelled`/`customer_code`. No rep column exists on ORCT itself; used only for `unallocated_amount`.
- `base_payment_apps` — `sap_payment_applications` joined `payment_ref → sap_payments.doc_entry` (RCT2 join trap), left-joined to `sap_invoices` on `doc_entry` filtered `inv_type = 13` to resolve `invoice_sales_rep_code`. When `p_sales_rep_code` is set, rows where that join didn't resolve (`inv_type != 13` — on-account cash, other doc types) are excluded — cash that can't be attributed to a rep can't pass a rep filter. Also excludes (as of 2026-07) any row whose matched invoice doesn't share the current `is_cancelled` filter state — previously a payment applied against a since-cancelled invoice still counted toward `totalCollected` even though that invoice's own revenue was excluded from `periodInvoicedRevenue`.
- `rep_collected_actuals` — per-`sales_rep_code` sum of `amount_applied_myr` from `base_payment_apps`, `payment_date` in range. Feeds `salesRepRevenueData.collected_myr` only.
- **`base_bills`** (added 2026-07) — `sap_vendor_bills` filtered by `is_cancelled`, `vendor_code`, `status_code`. AP mirror of `base_invoices` — no rep/GP-guard analog, since OPCH carries no `sales_rep_code` and its `GrosProfit` isn't a meaningful AP concept.
- **`base_vendor_payments`** (added 2026-07) — `sap_vendor_payments` (OVPM header), filtered by `is_cancelled`/`vendor_code`. AP mirror of `base_payments`, used only for `unallocated_amount`.
- **`base_vendor_payment_apps`** (added 2026-07) — `sap_vendor_payment_applications` joined `payment_ref → sap_vendor_payments.doc_entry` (VPM2 join trap), left-joined to `sap_vendor_bills` on `doc_entry` filtered `doc_type = 18` (mirrors the `inv_type = 13` filter on the AR side). No rep-code passthrough column — vendors don't have a "sales rep" concept.
- **`gl_account_ancestry_raw` / `gl_account_ancestry`** (added 2026-07) — a `WITH RECURSIVE` walk of `sap_gl_accounts.father_code`, starting from every postable (leaf) account, tagging each with its Level-2 and Level-3 chart-of-accounts ancestor codes. Needed because `account_code` is not a reliable textual prefix for the hierarchy (confirmed live: account `6200260` sits under drawer 5 despite its `"62..."` prefix). This is the one recursive CTE in the whole function — the function's `WITH` clause had to be declared `WITH RECURSIVE` to allow it; every other CTE here remains plain/non-recursive.
- **`gl_balance_sheet`** (added 2026-07) — one row per postable GL account with its `current_balance_myr` and resolved ancestry codes. Feeds the balance-sheet KPIs below directly from `sap_gl_accounts`' own maintained balance (not summed from `sap_gl_journal_lines`) — mirrors this RPC's existing "trust SAP's own maintained aggregate" pattern for `outstanding_ar`.
- **`base_gl_lines`** — reads from `private.mv_gl_monthly_account_summary` (added 2026-07, `hyrax-data-platform/infrastructure/gl_monthly_summary_migration.sql`; moved to the `private` schema by a follow-up, `gl_monthly_summary_private_schema_migration.sql`), **not** a live join, since `sap_gl_journal_lines`/`sap_gl_journal_entries`/`sap_gl_accounts` joined directly (467K + 156K rows, unconditionally full history on every call — the date filter only decides which rows count toward the sums, not how much gets scanned/joined) was still costing 10s+ even after `kpi_totals`'s single-pass `FILTER` rewrite. The materialized view pre-joins and pre-aggregates to `(month, account_code)` grain — a few thousand rows instead of hundreds of thousands — and **excludes `trans_type = '-3'`** at the view level (SAP Business One's own reserved system code for period-end closing entries — confirmed live: a March 2023 closing batch exactly canceled that fiscal year's entire revenue to the cent, and the pattern recurs across most historical fiscal years; without this exclusion, any fiscal year SAP has formally closed reports `netProfit`/`ebitda`/`plTrendData` as a misleading `RM 0`). Refreshed by `ingestion/sap_supabase/src/extractors/gl_journal.py` right after each GL pipeline run (`refresh_gl_monthly_summary()`), not on a schedule — no `pg_cron` is set up in this app. **Why `private`, not `public`:** Supabase's linter flagged the original `public`-schema version — a materialized view doesn't re-apply RLS from its source tables when queried directly, and sitting in `public` meant it was auto-exposed as a REST endpoint reachable by any API caller, bypassing the app's `AccessRoute`/`canAccess` gating entirely. Nothing but this RPC ever needed to read it, so it was moved to `private` (not in PostgREST's exposed-schemas list, so not routable via the API at all) with explicit `GRANT`s so this function's own internal query still succeeds — `get_finance_dashboard` itself stays `SECURITY INVOKER`, its existing correct default. **Known tradeoff:** `posting_date` is month-truncated (first-of-month), not the exact day, so a custom date range that doesn't land on a month boundary rounds to whole months for GL figures specifically (AR/AP figures are untouched) — fine in practice since the only real filter UI here is the Fiscal Year preset (April-March, always month-aligned). `base_gl_lines`'s own output columns are unchanged from the old live-join version, so nothing downstream (`gl_agg`, `plTrendData`, `opexBreakdownData`, `plYoyTrendData`) needed to change. Deliberately does not affect `gl_balance_sheet` — the balance sheet keeps reflecting the real current balance, including the equity increase a closing entry produces.
- **`invoices_agg` / `payment_apps_agg` / `payments_agg` / `bills_agg` / `vendor_payment_apps_agg` / `vendor_payments_agg` / `gl_agg` / `gl_balance_agg`** (added 2026-07, performance rewrite) — one single-pass aggregate CTE per base table above, each computing every field it owns via `sum(...) filter (where ...)` instead of a separate correlated subquery per field. `gl_agg` also folds in the `gl_account_ancestry` join (needed for `glPeriodInterest`'s "7200" lookup) as a `left join`, so that lookup no longer needs its own separate scan either. `kpi_totals` (below) is a plain cross join of these eight single-row results.
- **`gl_balance_history`** (added 2026-08, Phase 3) — reads `private.mv_gl_monthly_balance_sheet_snapshot` (`hyrax-data-platform/infrastructure/gl_balance_history_migration.sql`), joined to the existing `gl_account_ancestry` CTE for Level-2/Level-3 classification, filtered to `level2_ancestor in ('100','200','300','400')`. A second, purpose-built materialized view alongside `mv_gl_monthly_account_summary` — that one excludes SAP's period-end closing entries (correct for P&L, wrong for a balance-sheet reconstruction, since a closing entry's offsetting debit/credit typically lands on Equity), this one includes every posting.
- **`cf_start_balances` / `cf_end_balances`** (added 2026-08, Phase 3) — `distinct on (account_code) ... order by account_code, month desc`, the standard Postgres "latest row per group" idiom, picking each account's cumulative balance as of the most recent month-end before `p_start_date`/at-or-before `p_end_date` respectively. Both return zero rows (not an error) when the corresponding date parameter is null.
- **`cf_agg`** (added 2026-08, Phase 3; **corrected 2026-08 follow-up, see below**) — full-outer-joins the two CTEs above by `account_code` and sums into five category deltas: `delta_current_assets_excl_cash` (Level-2 `200`, excluding Level-3 `2600`/`2600 Cash and Bank Balances` **and `2500`/Fixed Deposits**), `delta_current_liabilities` (Level-2 `300`, excluding Level-3 `3200`/Short Term Borrowings), `delta_fixed_assets` (Level-2 `100`), `delta_equity` (Level-2 `400`), `delta_short_term_borrowings` (Level-3 `3200` — feeds `financingCashFlow` alongside `delta_equity`), plus `delta_cash` (Level-3 `2600` **and `2500`** together — cash and cash equivalents, used only for the reconciliation check below, never as a working-capital input).
  - **Follow-up fix (2026-08):** the first version treated _all_ of Level-2 `300`/Current Liabilities as operating and only excluded `2600` from `200`/Current Assets. A live reconciliation test reported material drift on both checks; walking the real `FatherNum` ancestry (not the account-code prefix) found `3200` "Short Term Borrowings" is a real Level-3 node under `300` holding -RM42.8M in active term loans/hire-purchase/trade-financing facilities (heavy 2026 drawdown/repayment activity) — genuine financing debt, not trade payables — and `2500` "Fixed Deposits" is a real Level-3 node under `200` (RM6.0M, real bank↔FD transfer activity) that belongs with cash equivalents, not working capital. Both reclassified accordingly. Checked and confirmed _not_ contributing at that point: `4100`/`4200` under Equity (`400`) had zero postings in the trailing 24 months — but see the second follow-up fix below, which found `4200` isn't actually dormant once tested per fiscal year.
  - **Second follow-up fix (2026-08):** testing full fiscal-year windows (not just trailing-months ones) surfaced material drift again. `mv_gl_monthly_balance_sheet_snapshot` didn't exclude SAP's period-end closing entries (`trans_type='-3'`) — confirmed live these touch only drawers 3 (Equity)/4-8 (P&L), never 1-2 — and each fiscal year-end posts that year's net P&L into `4200130 Period End Closing Account` on the _last day of the fiscal year being closed_, landing inside any full-FY test window and double-counting that year's net profit into `delta_equity` on top of what `netProfit` already counted. New follow-up migration `gl_balance_history_closing_entry_exclusion_migration.sql` excludes `trans_type='-3'` from the view (the original `gl_balance_history_migration.sql` is left unedited, per this repo's "never rewrite an already-run migration" convention). A second, independent bug found the same pass: depreciation posts monthly by crediting separate "Accumulated Depreciation" contra-asset accounts under `level2_ancestor='100'`, so `delta_fixed_assets` already has depreciation baked in every period — `investingCashFlow` now subtracts `gl_period_depreciation_amortization` to remove that double-count (see below). What legitimately remains after both fixes is predominantly a real, confirmed-live "Effect of Exchange Rate Changes on Cash" from SAP's fiscal-year-end FX revaluation of foreign-currency cash/loan accounts — a standard IAS 7 line, not a bug; see `cashFlowStatementData`'s row below for the reframed presentation.
- **`bank_movements_agg`** (added 2026-08, Phase 3) — `sum(debit_amount - credit_amount)` from `sap_bank_account_movements` where `due_date` falls in `(p_start_date, p_end_date]`. A second, independent reconciliation source — not derived from the same G/L journal lines every other Cash Flow figure comes from.
- **`kpi_totals`** — cross join of the eight `*_agg` CTEs from the performance rewrite, plus `cf_agg`/`bank_movements_agg` (added 2026-08). Every field name/formula downstream is unchanged from before the rewrite.

> **Why `periodInvoicedRevenue − totalCollected ≠ outstandingAR`, even with no date filter applied (confirmed 2026-07):** these three numbers are sourced from two structurally different places, not just different time windows. `outstandingAR` comes straight from `sap_invoices.paid_to_date` — SAP's own native, per-invoice running total (OINV.PaidToDate), with **no RCT2 join at all**. `totalCollected` comes from `base_payment_apps` (RCT2/`sap_payment_applications`), which can only attribute cash to `inv_type = 13` rows — on-account cash, credit memos, and other document types settle an invoice's `paid_to_date` in SAP without ever appearing in this sum. So `totalCollected` will generally **undercount** "true" cash collected relative to what `periodInvoicedRevenue − outstandingAR` implies — that gap is a real RCT2 attribution-coverage limit, not a bug in either individual figure. To quantify the gap on live data, compare SAP's own bookkeeping against the RCT2-derived figure directly:
>
> ```sql
> -- SAP's own "paid so far" across all active invoices (mirrors periodInvoicedRevenue - outstandingAR)
> select sum(total_amount_myr) as invoiced, sum(paid_to_date) as paid_per_sap,
>        sum(total_amount_myr - paid_to_date) as unpaid
> from sap_invoices where is_cancelled = 'N';
> -- RCT2-derived collected, same population, split by inv_type to see where the gap concentrates
> select pa.inv_type, count(*), sum(pa.amount_applied_myr)
> from sap_payment_applications pa join sap_payments p on pa.payment_ref = p.doc_entry
> where p.is_cancelled = 'N' group by pa.inv_type order by 3 desc;
> ```

## `get_sales_reports_dashboard`

Backs Sales Reports (`Reports.jsx`). Surfaces two forecasts side by side, deliberately never blended: Forecast 1 "Pipeline Target" (CRM self-reported, `sales_targets`/`sales_leads`) and Forecast 2 "Invoice Budget" (a manually-set revenue budget, `sales_budgets` — not an SAP extract itself — compared against SAP-invoiced actuals, `sap_invoices`) — plus, as of 2026-07, the company's actual sales-side review: **PO (sales order) vs Invoice vs Budget variance, per rep.** See `DASHBOARD-CONVENTIONS.md`'s "Source-labeling convention" for the full tag vocabulary (Target/Budget/Sales Order/Invoice) this RPC's consumers use.

**Redesigned 2026-07** (mirroring the Finance Reports redesign) to align with `sap-data-architecture-plans/02-department-kpi-frameworks.md`'s Sales KPI framework: added a pipeline-stage funnel, a forward-looking pipeline coverage ratio, a synthesized pipeline-velocity metric, and a SAP-only bookings-vs-invoiced trend. See the field tables below and `DASHBOARD-ROADMAP.md`'s dated entry for the full before/after tile disposition.

**Rebalanced 2026-07** (invoice/budget/collected pass): the company's real day-to-day focus is invoices, budget, and collected cash, not the CRM pipeline — this RPC previously had **zero visibility into cash collection**. Added the `base_payment_apps` RCT2→ORCT→OINV chain (copied from `get_finance_dashboard_rpc.sql`'s own CTE of the same name) powering `totalCollected`/`collectionRatePct`/a 4th scorecard leg/a 3-series trend chart; added a dept-wide `totalInvoiced`/`invoiceCount`/`avgInvoiceValue` (this RPC previously had no dept-wide invoiced figure in `kpis` at all); and converted the Customer Concentration tile's data source from CRM (`topClientsData`/`pipelineWonRevenue`) to SAP-invoiced (`topInvoicedCustomersData`/`totalInvoiced`), mirroring Finance's `topCustomersByRevenueData`. `topClientsData` itself is unchanged and still feeds the CRM-side "Top Clients" chart only.

**Signature:**

```
get_sales_reports_dashboard(
  p_start_date   date default null,
  p_end_date     date default null,
  p_owner_id     uuid default null,               -- CRM lead owner (employees.id) -- scopes BOTH forecasts, see below
  p_product_type public.product_type default null
)
```

**Access guard + salesperson scoping (added 2026-08).** This RPC has no RLS backstop on any table it reads (`sap_*`, `sales_leads`, `sales_budgets` — see `supabase/access-control/table_access_matrix.csv`), so it now opens with a hand-rolled guard mirroring `get_finance_dashboard_rpc.sql`'s own: resolves the caller's role/department/`employees.id` from `profiles`/`roles`/`departments`/`employees` via `auth.uid()`, `raise exception`s unless the caller is `superadmin` or in `SAL`/`MGM`, and — for a `staff`-role caller — force-overrides `p_owner_id` to their own `employees.id`, ignoring whatever value was actually passed. This is currently unreachable from the frontend (`sales/reports` stays `departments={["SAL","MGM"]} roles={["manager"]}`-gated) but closes the direct-call bypass hole for every caller today, and is the foundation a future self-service surface plugs into without any further RPC change (see `DASHBOARD-ROADMAP.md`'s Sales Reports section).

The (possibly-overridden) owner id is then resolved **once** to a SAP `sales_rep_code` via `employee_sales_rep_mapping`, and that resolved code scopes every SAP-sourced base CTE — **`p_owner_id` now scopes both forecasts**, not just Forecast 1/CRM as before. (Previously: "No `p_sales_rep_code` parameter exists — the per-rep datasets below always return every rep, unfiltered by SAP identity." That asymmetry is fixed.)
